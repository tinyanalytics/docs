An API key authenticates programmatic analytics reads, site management, scoped SQL, and MCP. It is
not part of client-side tracking: the browser script and its event and identity methods are keyless.

Create either a full-access key or a restricted key with per-resource permissions in **Settings →
Account**, then send it as a Bearer token:

<CodeGroup>

```bash cURL
curl https://dash.tinyanalytics.io/api/sites/1/overview \
  -H "Authorization: Bearer YOUR_API_KEY"
```

```js Node.js
await fetch("https://dash.tinyanalytics.io/api/sites/1/overview", {
  headers: { Authorization: "Bearer YOUR_API_KEY" },
})
```

```python Python
import requests

requests.get(
    "https://dash.tinyanalytics.io/api/sites/1/overview",
    headers={"Authorization": "Bearer YOUR_API_KEY"},
)
```

</CodeGroup>

## Create and manage keys

- A key is **shown once** at creation. Copy it then; TinyAnalytics stores only a hash and cannot show
  it again.
- **Revoke** a key any time to cut off its access immediately.
- A key inherits **its owner's access**. Organization membership, role, and [team](/team-site-access)
  access still apply.
- Leave **Restrict permissions** off for full access, or turn it on and select at least one resource
  for a least-privilege key.

## Available permissions

| Resource | Available access | What it covers |
| --- | --- | --- |
| **Analytics** | Read | Traffic, acquisition, retention, revenue, performance, errors, and heatmaps. |
| **Sessions** | Read | Visitor sessions and their activity. |
| **Events** | Read / Write | Event reports and catalog descriptions. |
| **Users** | Read / Write | Visitor profiles, traits, profile management, and erasure. **Users: Read** also covers user-trait reads and `trait:<key>` filters. |
| **Goals** | Read / Write | Conversion goals. |
| **Funnels** | Read / Write | Conversion funnels. |
| **Dashboards** | Read / Write | Dashboards, cards, and annotations. SQL-backed card preview separately needs **Custom SQL: Read**. |
| **Workflows** | Read / Write | Workflow definitions, versions, runs, and metrics. API-key mutation is not available in workflow version 1. |
| **Sites** | Read / Write | Sites, tracking setup, configuration, and deletion. |
| **Custom SQL** | Read | Read-only, site-scoped SQL. |

Selecting **Write** also selects **Read** for that resource when both actions exist. It does not
grant access to any other resource. Existing keys created without a permission list remain
full-access keys.

<Note>
  For workflows, use **Workflows: Read**. Creating, editing, publishing, testing, pausing, resuming,
  archiving, and cancelling require an owner or admin signed in with a dashboard session in workflow
  version 1.
</Note>

<Note>
  A restricted key with **Sites: Read** can list the organizations and sites its owner may access,
  but organization-list responses omit member rosters. Dashboard sessions and existing full-access
  keys retain the complete member directory.
</Note>

<Note>
  Trait data can contain names and emails, so user-trait reads and `trait:<key>` filters require
  **Users: Read**. Trait filters do not run on a public site, share link, or embed.
</Note>

<Warning>
  Treat an API key like a password. Never ship it in browser code, a public bundle, a URL, or a log.
  Revoke an exposed key immediately. Browser tracking needs no key; the snippet's `data-site-id`
  identifies the site.
</Warning>

## Where a key is required

| Use | Needs a key? |
| --- | --- |
| [Browser events](/api-reference/track-events-api) | No. |
| [Browser identity](/api-reference/identify-users-api) | No. |
| [Analytics reads](/api-reference/analytics-read-api) | Yes, unless the site is public. |
| [Scoped SQL query](/api-reference/sql-analytics-api) | Yes. |
| Site and analytics configuration management | Yes. |
| [MCP server](/api-reference/mcp-server) | Yes. Your AI client sends it as a request header. |

## Send the key safely

Always send the key in the `Authorization` header, never in the URL. A key in a query string can leak
into logs, browser history, and referrer headers.

```
Authorization: Bearer YOUR_API_KEY
```

## Frequently asked questions

<AccordionGroup>
  <Accordion title="I lost my API key — can I see it again?">
    No. Create a new key in account settings and revoke the old one.
  </Accordion>
  <Accordion title="Can I use an API key in client-side code?">
    No. Use the keyless browser APIs for events and identity. API keys can expose private data and
    management actions when bundled into client-side code.
  </Accordion>
  <Accordion title="What can someone do with a leaked API key?">
    A full-access key can use every API capability its owner can access. A restricted key can use
    its selected resources and actions, still bounded by the owner's permissions. Revoke either key
    immediately.
  </Accordion>
  <Accordion title="Does write include read access?">
    Yes, but only for the same resource. Selecting **Goals: Write**, for example, also selects
    **Goals: Read**; it does not grant access to Funnels, Sites, or another resource.
  </Accordion>
  <Accordion title="How often can I create API keys?">
    API-key creation is limited to 10 attempts per signed-in user each hour. Invalid creation
    requests count toward the same limit. A `429` response includes `Retry-After`.
  </Accordion>
</AccordionGroup>
